# 采访 Skill（Career-Wiki-Skill）

## 概述

通过 7 节问题树采集求职者完整信息。**混合模式**：基本信息填表式快过，经历/项目让用户自由讲再提取确认。产出是原始 markdown（保留用户原话），不预结构化——结构化提取是 wiki 引擎 compile 的活。

## 何时触发

- 用户说"开始采访 / 录入信息 / 填一下简历信息"
- 用户主动讲了一段经历、一个项目、一个技能
- 用户说"补一下 / 补充 / 上次漏了"
- 上一轮采访产出已 compile，用户要追加

**不用于：** 用户上传文件（用 file-parser skill）；直接编辑 wiki 页面（用户应改 raw 再 recompile）。

## 数据目录约定

- 存储：`~/.career_wiki/sources/raw/interview-{YYYYMMDD-HHmmss}.md`
- 续采时 round 递增（首轮 round=1，第一次补 round=2）
- 所有路径以 `~/.career_wiki` 为根，Agent 首次调用先确认该目录存在；不存在则提示用户先跑 env-init skill

## 产出文件格式

每个采访产出文件结构：

```markdown
---
interview_date: 2026-07-31
round: 1
interviewer: career-wiki-skill
---

# 基本信息
（用户原话或填表内容）

# 工作经历
## 经历 1
（用户原话）

...

# 项目经验
## 项目 1
（用户原话）

...
```

**保留用户原话。** 用户自由讲的部分用引用块 `>` 记录原话，Agent 的提取确认用普通文本跟在后面。项目回答的完整原话必须写入 raw，不能只保留面向简历的摘要。不做 frontmatter 实体提取——那是 compile 的活。

## 采访流程

### 阶段 0：开场定位

> 🔴 **CHECKPOINT** — 开始采访前必须完成以下确认
>
> 1. 确认 `~/.career_wiki/` 存在；不存在 → 🛑 STOP，提示用户先跑 env-init
> 2. 如果是续采，先读上一轮 raw 文件，告诉用户已有什么、问要补哪节
> 3. 如果首轮，说明流程："我会按 7 节问，基本信息快过，经历项目你自由讲我来整理确认"
>
> 🛑 目录不存在时不要继续。没有数据目录，采集的内容无处可写。

### 阶段 1：基本信息（填表式快过）

逐项确认，能快就快：

| 字段 | 问法 | 必填 |
|------|------|------|
| 姓名 | "你叫什么？" | 是 |
| 当前职位 | "现在/最近的职位？" | 是 |
| 求职意向 | "想找什么样的工作？" | 是 |
| 邮箱 | "联系邮箱？" | 否 |
| 电话 | "电话？" | 否 |
| 所在地 | "在哪个城市？" | 否 |
| GitHub | "GitHub 用户名/链接？" | 否 |
| 个人网站 | "有个人网站或博客吗？" | 否 |

用户一次性倒出来全填了更好，不必逐项追问。缺必填项时再补问。

### 阶段 2：工作经历（自由讲 + 提取确认）

**循环结构**（每段经历走一遍）：

1. **开场**："讲一段工作经历吧，公司、职位、做了多久、主要做什么"
2. **用户自由讲** → Agent 用 `>` 引用块记原话
3. **Agent 提取确认**：把用户讲的结构化复述一遍让用户确认——
   - 公司名 / 职位 / 起止时间（YYYY-MM 或 YYYYMM-YYYYMM）/ 类型（全职/兼职/实习）/ 薪资（可选，用户不主动问）
   - 复述："我确认一下：你 2023.06-2024.09 在字节跳动做后端开发，全职，对吗？"
4. **追问项目**：这段工作期间有没有想展开讲的项目？有 → 标记，阶段 3 展开
5. **追问技能**：这段用到的技能？有 → 标记，阶段 4 展开
6. **循环判断**："还有其他工作经历要补吗？" → 有则回到步骤 1

### 阶段 3：项目经验（单题串行 + 提取确认）

**循环结构**（每个项目走一遍）：

1. **开场只问一题**："先介绍一下这个项目是做什么的？"
2. **记录与提取**：用 `>` 引用块完整记录原话，并从回答中标记已经明确的信息；用户主动多讲的内容直接记录，不再重复询问。
3. **建立缺口队列**：把尚未明确的项目按以下顺序放入队列，但不要把问题清单一次性展示给用户——
   - **项目名称**："这个项目叫什么？"
   - **所属经历**："这个项目属于哪家公司或组织？"
   - **起止时间**："这个项目从什么时候做到什么时候？"
   - **项目角色**："你在这个项目中的角色是什么？"
   - **项目描述**："这个项目主要解决什么问题？"
   - **本人职责**："你在这个项目中具体负责什么？"
   - **技术栈**："项目用到了哪些语言、框架、数据库、云服务或工具？"
   - **困难**："过程中遇到的主要困难或约束是什么？"
   - **解决方案**："你最终采用了什么解决方案？"
   - **结果（有则追问）**："这个项目最终取得了什么结果？"
   - **复盘（有则追问）**："如果重做一次，你最想改进什么？"
   - **项目链接（可选）**："这个项目有可以记录的链接吗？"
4. **严格串行补问**：每轮只发送一个问题，然后停止并等待用户回答，禁止在同一条消息中询问多个问题。
5. **清晰度判断**：回答必须具体到能够不依赖 Agent 猜测而写入对应字段。回答不明确、过于笼统或存在歧义时，只围绕当前问题提出一个有针对性的追问，并再次等待用户回答；此时不得进入下一问题。
6. **当前项完成**：必要时用一句话复述当前答案让用户确认。当前答案明确后才标记完成，并开始询问缺口队列中的下一问题。
7. **整理结果**：每一项都在当前问题中完成确认和记录；全部问题结束后只能陈述整理结果，不再要求用户一次确认多个字段，也不夹带新的补问。
8. **确认边界**：告诉用户这些回答会完整存档到知识库，生成简历时再按岗位选择，不会把全部内容强行放进简历。
9. **循环判断**："还有其他项目吗？"

串行补问的状态只能按以下方向推进：

```text
取当前缺口 → 询问一个问题 → 等待回答 → 判断是否明确
                                      ├─ 否：追问当前问题 → 等待回答
                                      └─ 是：记录当前项 → 进入下一缺口
```

项目原话在 raw 中应保持完整叙述，确认结果可以按以下小标题组织，便于 Wiki 编译时准确提取：

```markdown
### 项目描述
### 本人职责
### 技术栈
### 困难
### 解决方案
### 结果
### 复盘
```

### 阶段 4：技能（填表式 + 自由补充）

逐个列：

1. **引导**："列出你的技能，每个说下名称、分类（语言/框架/工具/数据库/云/方法论/其他）、熟练程度（了解/熟悉/掌握/精通）"
2. 用户一次性倒或逐个讲都行
3. **Agent 提取确认**：复述每个技能的结构化信息让用户确认
4. **循环判断**："还有要补的技能吗？"

### 阶段 5：教育背景（填表式 + 循环）

**循环结构**（每段教育走一遍）：

1. 学校 / 学历（专科/本科/硕士/博士/其他）/ 专业 / 起止时间 / GPA（可选）/ 课程（可选）
2. **循环判断**："还有其他教育经历吗？"

### 阶段 6：证书 / 获奖 / 发表 / 活动（逐类循环）

四个子节，每个都走循环：

**证书**（name / issuer / date / url?）→ "还有证书吗？"
**获奖**（name / issuer / date / description?）→ "还有奖项吗？"
**发表**（title / venue / date / url?）→ "还有发表吗？"
**活动**（name / role(maintainer/contributor) / start / end / url? / description?）→ "还有活动吗？"

没经历的子节直接跳过，别空问。

### 阶段 7：个人优势总结

1. **首选**：让用户自己讲——"用一段话总结你的核心优势和求职亮点"
2. 用户讲不出来 → Agent 说"我从刚才采集的信息帮你总结一下，你看看对不对"，从经历/项目/技能提炼 3-5 条优势让用户确认
3. 记录为 summary，type 标注 personal（用户自写）或 auto-summary（Agent 总结用户确认）

### 阶段 8：写文件 + 触发 compile

> 🔴 **CHECKPOINT** — 触发 compile 前必须完成以下确认
>
> 1. 向用户确认：采访已结束，即将写入 raw 文件并触发 wiki 引擎 compile
> 2. 告知用户 compile 可能需要时间（有 subagent 则并行，无则同步阻塞）
> 3. 用户确认后，执行以下步骤：
>
> 1. 用 `write_file` 写 `~/.career_wiki/sources/raw/interview-{timestamp}.md`
>    - frontmatter：`interview_date / round / interviewer: career-wiki-skill`
>    - 正文按 7 节组织，用户原话用 `>` 引用块，Agent 确认用普通文本
> 2. **自动触发 wiki 引擎 compile**（F04）：
>    - **有 subagent 能力**：并行触发 compile，不阻塞用户
>    - **无 subagent 能力**：同步执行 compile，跑完告诉用户"已编译进 wiki"
> 3. 告诉用户文件路径 + compile 状态

## 续采支持

用户后续补信息时的流程：

1. 读最新的 raw 文件，看 round 号，新文件 round+1
2. **用户明确说补什么** → 直接进对应节（如"补一个项目"→ 阶段 3 流程）
3. **用户不明确**（如"再补充点"）→ 引导："上次采集到 round {N}，工作经历/项目/技能都有了吗？要补哪节？"
4. 续采只写新增内容到新文件，不改旧文件（compile 时全量合并所有 raw）

## 跨 Agent 一致性

- 假设所有支持 skill 的 Agent 有基本对话能力（能问问题、记回答、写文件）
- **不做降级**——如果 Agent 不支持 subagent 并行，就同步跑 compile
- 问题树和产出格式是硬约束，对话风格可适配

## Common Pitfalls

1. **在采访阶段做结构化提取。** 采访只记原话 + 确认复述。实体 frontmatter 化是 wiki 引擎 compile 的事。混在一起会让 raw 文件难读且难维护。

2. **覆盖旧 raw 文件做续采。** 每轮采访写新文件，round 递增。compile 全量扫所有 raw 重建 wiki，不会漏。

3. **填表式对待自由讲节。** 阶段 2/3/7 是自由讲 + 确认，别逐字段追问把用户问烦。用户讲完再结构化复述确认即可。

4. **空问没经历的节。** 阶段 6 四个子节，用户没证书就跳过，别每个都问"有没有"。

5. **忘记触发 compile。** 阶段 8 写完文件必须调 wiki 引擎。有 subagent 就并行，没有就同步，不能跳过。

6. **主动问薪资。** 薪资是可选字段，除非用户主动提，不要追问。

7. **只保留简历摘要。** 项目困难、解决过程、结果和复盘即使暂时不展示，也必须保留在 raw 中，供后续 Wiki 编译和定向简历使用。

8. **一次抛出多个问题。** 项目补问必须逐题进行；即使缺口很多，也只能在用户答清当前问题后再问下一题。
